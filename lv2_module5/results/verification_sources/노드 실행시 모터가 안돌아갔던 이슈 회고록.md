# LIVE 객체 추적 테스트 회고록

## 1. 현상

카메라에서 객체가 검출되고 `TRACKING` 상태까지 올라왔지만, OpenCR 모터가 움직이지 않거나 특정 각도에서 멈춘 뒤 다시 움직이지 않았다.

## 2. 가장 큰 원인

### OpenCR의 준비 상태 전이 순서가 지켜지지 않음

OpenCR 펌웨어는 안전을 위해 다음 순서를 요구한다.

```text
RESET → BOOT 확인 → /opencr/prepare → READY 확인
→ stop=false 제어 명령 확인 → /opencr/arm
```

다음 오류는 이 순서가 지켜지지 않았다는 뜻이다.

```text
Requires a fresh BOOT state; reset firmware first
```

`/opencr/prepare`를 여러 번 호출해도 OpenCR이 새 `BOOT` 상태가 아니면 준비되지 않는다. OpenCR RESET 버튼이나 USB 재연결로 먼저 새 BOOT 상태를 만들어야 했다.

또한 다음 오류는 인지 결과가 있어도 아직 모터를 ARM할 조건이 안 된 경우다.

```text
Requires a fresh stop=false ROS command; no automatic ARM
```

객체가 검출되고 `/control/pan_tilt_cmd`에 `stop: false`가 나온 뒤에만 ARM해야 한다.

## 3. 펌웨어 빌드·업로드 과정의 문제

처음에는 잘못된 FQBN으로 빌드했다.

```text
OpenCR:OpenCR:OpenCR
```

수동 설치된 코어의 올바른 FQBN은 다음이었다.

```text
ROBOTIS:OpenCR:OpenCR
```

올바른 FQBN으로 빌드한 뒤 `.bin` 파일이 생성되는 것까지 확인했지만, 빌드 성공만으로 OpenCR에 새 펌웨어가 올라간 것은 아니다. 실제 업로드에서는 `CRC OK`와 `[OK] Download`를 확인해야 한다.

또한 소스와 OpenCR에 실제로 올라간 펌웨어가 다르면 ROS 쪽에서 기대하는 상태 전이와 보드의 동작이 달라질 수 있다. 따라서 소스를 수정한 뒤에는 반드시 다음 과정을 다시 해야 한다.

```text
소스 checkout 확인 → Arduino CLI compile → .bin 확인
→ OpenCR 업로드 → STATUS 확인 → ROS 실행
```

## 4. 중립 위치·각도 한계 문제

초기 펌웨어는 고정된 중립값과 비교해 중립 위치를 벗어나면 보드가 다음과 같은 FAULT를 발생시켰다.

```text
BOARD_FAULT SUPPORT_AT_NEUTRAL SUPPORT_CAMERA
```

당시 실제 모터 위치와 펌웨어가 기대하는 중립 위치가 달라서 `/opencr/prepare` 단계에서 막혔다.

이 문제를 해결하기 위해 `3270103` 커밋에서 실행 시 현재 정지 위치를 기준으로 삼고 추적 한계를 넓혔다. 이후 한계 처리 동작을 변경한 `be2cf59`는 사용자의 요청에 따라 `98d8684` revert 커밋으로 되돌렸다.

현재 `dev/test1`의 기준은 다음과 같다.

```text
3270103 상태의 펌웨어 동작
```

따라서 현재 소스와 실제 OpenCR 펌웨어가 일치하는지 확인하는 것이 중요하다.

## 5. 각도 한계에서 멈춘 뒤 재추적하지 못한 이유

기존 `LIMIT` 처리에서는 한계 방향 명령이 들어오면 모터를 정지시키면서 ARM을 해제하는 동작이 포함되어 있었다. 그래서 객체가 반대 방향으로 이동해도 ROS 제어 명령이 다시 들어와도 모터가 움직이지 않았다.

`be2cf59`에서는 ARM 상태를 유지하고 한계 방향 축의 명령만 0으로 만드는 방식으로 바꿨지만, 현재는 사용자의 요청으로 이 변경을 되돌린 상태다.

즉 현재 버전에서는 각도 한계에서 멈춘 뒤 반대 방향 재추적이 다시 필요한 경우, 기존 `LIMIT` 처리 방식 때문에 다시 ARM해야 하거나 정지 상태가 유지될 수 있다.

## 6. 카메라 USB 문제

RealSense 노드는 실행됐지만 영상 토픽이 발행되지 않는 경우가 있었다.

```text
/camera/camera/color/image_raw
WARNING: topic ... does not appear to be published yet
```

D435 USB를 뺐다가 5초 후 USB 3 포트에 다시 연결하면 영상이 정상적으로 올라왔고, 다음처럼 약 30 Hz가 확인됐다.

```text
/camera/camera/color/image_raw ≈ 30 Hz
```

카메라가 정상적으로 연결되지 않으면 인지 노드가 입력 영상을 받지 못하므로 `/target`과 제어 명령도 나오지 않는다.

## 7. ROS 노드와 토픽 확인 부족

`/target`이 정상적으로 출력되고 `TRACKING`이 나와도 모터가 바로 ARM되는 것은 아니다. 각 단계별로 다음을 확인해야 한다.

```text
카메라 영상 30 Hz
→ /target 출력
→ /tracking_status = TRACKING
→ /control/pan_tilt_cmd 출력
→ stop: false
→ /opencr/prepare 성공
→ READY
→ /opencr/arm 성공
```

특히 `/control/pan_tilt_cmd`가 보이지 않을 때는 `control_node`가 실행됐는지와 `/target`을 구독하는지 확인해야 한다.

```bash
ros2 node list
ros2 node info /control_node
```

`/control_node`의 정상 상태는 다음과 같다.

```text
Subscribers:
  /target
Publishers:
  /control/pan_tilt_cmd
```

## 8. ROS 네트워크 설정 문제

모든 노드를 라즈베리파이 한 대에서 실행할 때는 다음 설정을 사용한다.

```bash
export ROS_DOMAIN_ID=77
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
```

다른 PC에서 라즈베리파이의 ROS 토픽을 확인할 때는 양쪽 모두 다음을 사용해야 한다.

```bash
export ROS_DOMAIN_ID=77
export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
export ROS_LOCALHOST_ONLY=0
```

`LOCALHOST`를 사용하면 같은 라즈베리파이 안의 터미널끼리만 발견되고 다른 PC에서는 서비스나 토픽을 찾지 못한다.

## 9. 최종 교훈

이번 문제는 단일 원인이 아니라 다음 조건들이 겹쳐서 발생했다.

1. OpenCR이 새 BOOT 상태가 아닌데 `prepare`를 호출함
2. `stop=false` 명령 확인 전에 ARM을 호출함
3. 카메라 USB 연결 상태가 불안정해 영상 입력이 끊김
4. 카메라 인지와 모터 제어 토픽을 같은 단계로 착각함
5. 잘못된 FQBN으로 펌웨어 빌드를 시도함
6. 수정한 소스를 빌드·업로드하지 않고 테스트할 가능성이 있었음
7. 다른 PC에서 `LOCALHOST` discovery를 사용함
8. 각도 한계에서 기존 펌웨어가 ARM을 해제함

앞으로는 `RASPBERRYPI_LIVE_TEST_RESTART.md`의 터미널 1·2·3 순서를 지키고, 모터 ARM 전에는 반드시 다음 세 가지를 확인한다.

```text
/camera/camera/color/image_raw ≈ 30 Hz
/target 출력 및 TRACKING
/control/pan_tilt_cmd의 stop: false
```
